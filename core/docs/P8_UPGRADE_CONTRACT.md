# P8 Generated Project Upgrade & Migration Contract

## Purpose

P8 adds safe evolution for projects that were already generated by an earlier Factory version. Factory lifecycle and project lifecycle remain separate: installing a newer Factory never mutates an existing project by itself.

## State machine

```text
Existing project
  -> DryRun plan
  -> READY | CURRENT | BLOCKED
  -> exact plan-hash confirmation
  -> targeted local rollback point
  -> Factory-owned overlay apply
  -> verification
  -> Factory Overlay Manifest
  -> updated Project Lock
```

## DryRun

DryRun is read-only. It records target paths, action, ownership, current/preimage/proposed hashes, a bounded unified diff preview for text changes, risk, blockers, verification gates, and rollback scope.

`CURRENT` means the project already satisfies the current Factory upgrade contract. `BLOCKED` means no apply is allowed. `READY` is necessary but not sufficient: apply still requires the exact DryRun `plan_sha256`.

## Ownership boundary

P8 migrates only Factory-owned overlay files. Business/source files are not migration targets. For legacy P7 projects, ownership preimages are recovered from the generation-time `PROJECT_MANIFEST.sha256`. P8 projects additionally record `managed_files` and a Factory Overlay Manifest.

A Factory-owned target whose current hash differs from its recorded preimage is a conflict and blocks migration. P8 does not silently merge or overwrite that file.

## Blueprint boundary

The persisted Blueprint must still match the Blueprint hash recorded in Project Lock. A semantically changed Blueprint requires explicit reconciliation before migration; P8 does not guess whether such a change is intentional.

## Provider boundary

P8 does not perform Provider migration. Existing-project verification is pinned to the exact Provider id/version in Project Lock. If that exact Provider is unavailable or the runtime version differs, migration blocks rather than silently selecting a newer or different Provider.

## Rollback point

Before the first overlay write, P8 creates a targeted preimage ZIP next to the project under `.project-factory-rollback/`. This is an immediate undo artifact, not an independent disaster backup.

After successful apply, a postimage receipt is written next to the rollback ZIP. Rollback verifies current postimages before restoring preimages, so it refuses to overwrite edits made after the upgrade.

P8 does not perform hidden automatic rollback after an apply failure. The rollback artifact is preserved and the failure is surfaced.

## Manifest boundary

`PROJECT_MANIFEST.sha256` remains the generation-time project snapshot. P8 does not re-baseline or hash the whole evolved project during migration.

Upgrade integrity is recorded separately in `.project/FACTORY_OVERLAY_MANIFEST.sha256`, which hashes only Factory-owned overlay files plus Project Lock and migration evidence.

## Verification

A successful apply requires:

- managed overlay postimages;
- canonical Agent Contract / Harness context parity;
- the locked Profile verification suite using the locked Provider version;
- Factory Overlay Manifest integrity.

The resulting status remains evidence-scoped. A browser extension can remain PARTIALLY_VERIFIED after a successful migration if real browser runtime claims are still unverified.

## Non-goals

P8 does not:

- automatically update projects when Factory updates;
- migrate Provider versions;
- rewrite business/source files;
- perform arbitrary three-way merges;
- download upstream artifacts;
- turn a local rollback point into a claimed disaster backup;
- refresh the generation-time Project Manifest.
